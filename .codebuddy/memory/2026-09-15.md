- 现象：后端启动报 `Found more than one migration with version 3.0.0.21`，`schedulerStarter`/`flywayInitializer` 起不来。
- 根因：源目录 `src/main/resources/migration/3.0.0/dml/` 里同时存在两份付款权限 DML：

  - `V3.0.0_32__ad_payout_pay_permission.sql`（上次会话 `git mv` 重命名后的正确版，已跟踪）
  - 空 21 文件 + ddl 的 `V3.0.0_21__ad_order_change_add_order_status_before.sql` 撞版本。
- 用户感知"没改 SQL 却起不来"：因为上次会话 `git mv` 到 32 后，旧 21 文件以空文件形式残留且未提交（untracked），增量编译仍把它拷进 `target/classes`，复现冲突。
- 修复：删除 `src` 与 `target/classes` 两处 0 字节的 `V3.0.0_21__ad_payout_pay_permission.sql`（空文件，删之无损），重启后端即可。
- 提醒：遇到 Flyway 版本冲突，先 `dir` 两目录确认是否撞版本，并留意 **0 字节未跟踪残留文件**。
- **关键根治点（已第三次踩到）**：残留空文件 `V3.0.0_21__ad_payout_pay_permission.sql` 反复出现，**根因在于 `src/main/resources/migration/3.0.0/dml/` 源目录那份**。maven 打包会原样把 `src/migration` 拷进 `target/classes`，所以**只删 target 副本没用，下次 `mvn package/clean package` 又会从 src 复制回来**。必须删 `src` 源目录那份才是根治；删完后 `git status` 该目录应无 `??` 未跟踪项。若再复发，说明用户环境（IDE Local History / 云盘同步 / git stash）在反复重建该 0 字节文件，需排查来源进程。

- **问题3**（表格展示不全且无法横向滚动）：`contract/index.vue` 两个 `n-data-table` 都**没传 `scroll-x`**，列宽合计（合同 tab 1540 / 已删除 tab 1700）超出容器时末列被裁剪且不出现滚动条。
  - 修复：新增 `tableScrollX` computed（`activeTab==='deleted' ? 1760 : 1600`），两个表格都绑定 `:scroll-x="tableScrollX"`。
  - **通用规则**：`n-data-table` 列宽合计 > 容器宽度时必须显式给 `scroll-x`，Naive UI 不会自动开启横向滚动。
- **问题4**（已删除列表「作废原因」列显示 `-`，但详情页能看到原因）：**列表接口没查这个字段**。`ExtAdContractMapper.xml` 的 `pageDeletedList`/`pageList` 的 SELECT 里没有 `c.void_reason`，且列表响应 DTO `AdContractListResponse` 也没有 `voidReason` 属性 → 前端 `row.voidReason` 恒为 undefined。
  - 修复：① `AdContractListResponse` 加 `private String voidReason;`；② 两个 SQL 的 SELECT 各加一行 `c.void_reason AS voidReason,`。
  - **教训/通用清单**：给列表页加一个后端字段，必须**三处齐全**才生效 —— (a) mapper XML SELECT 加 `列 AS 别名`（别名要等于 DTO 属性名）；(b) 列表响应 DTO 加同名字段；(c) 前端 model 加字段 + 列 render 取值。少任一处都是"页面空白/显示 -"，而详情页走的是另一套 DTO（`AdContractDetailResponse` 直接返实体），所以详情正常、列表为空。
  - 注意：`AdContractListResponse` 的 `statusLabel/sealStatusLabel/...` 等标签字段**不在 SQL 里**，由 `AdContractService.page/pageDeleted` 查询后循环 `setXxxLabel(...)` 填充；而 `voidReason` 是原始字段，必须走 SQL 取。
- **验证**：`read_lints` 对 index.vue/detail.vue/adContract.ts/AdContractListResponse.java/ExtAdContractMapper.xml 均 0 错误。

## 新增权限必须同步「四处」（角色管理页面看不到新权限的坑）
- **问题**：合同作废流程的 `AD_CONTRACT:VOID_SUBMIT` / `AD_CONTRACT:VOID_APPROVE` 在「系统 → 角色权限 → 广告合同」下**没有出现**，无法勾选分配。
- **根因**：权限码在 `PermissionConstants.java` 里加了、后端接口也用 `@CsPermission` 拦了，但**角色管理页面的权限树不是从 PermissionConstants 生成的**，而是由独立文件 `backend/crm/src/main/resources/permission.json` 提供（`RoleService` 读取后按 `permission.<小写末段>` 取 i18n 名，如 `AD_CONTRACT:ARCHIVE_APPROVE` → `permission.archive_approve`）。
- **完整清单（缺任一都白搭）**：
  1. `common/constants/PermissionConstants.java` —— 权限码常量（后端接口 `@CsPermission` 引用它）
  2. `backend/crm/src/main/resources/permission.json` —— **角色管理页面的权限树**（新权限最常被漏掉的就是这里）
  3. `backend/crm/src/main/resources/i18n/cordys-crm_zh_CN.properties` + `cordys-crm_en_US.properties` —— 权限显示名（key = `permission.` + 权限码冒号后的小写，如 `permission.void_submit`）
  4. 角色授权（DB `sys_role_permission`）—— 通过新 Flyway 迁移播种
- **前端**：`v-permission="['AD_CONTRACT:VOID_SUBMIT']"` 等直接用权限码字符串，与后端/PermissionConstants 保持一致即可，前端**没有** permission 树文件（`permission.json` 仅后端一份；`target/classes/permission.json` 是构建副本，勿改）。
- **本次落地**：
  - `permission.json` 的 `AD_CONTRACT` 节点下补 `VOID_SUBMIT` / `VOID_APPROVE`
  - zh/en properties 各加 `permission.void_submit=提交作废` / `permission.void_approve=作废审批`（英文 Submit Void / Void Approve）
  - 新增 `migration/3.0.0/dml/V3.0.0_37__ad_contract_void_permission.sql`：幂等 `INSERT ... SELECT ... WHERE NOT EXISTS` 授予 `org_admin`(管理员) 与 `ROLE_BOSS`(管理组) 两个权限，`ROLE_MEDIA`(媒介) 授予 `VOID_SUBMIT`。模板照抄 `V3.0.0_15__ad_permissions_v2.sql`（`sys_role_permission(id, role_id, permission_id)`，id 用 `UUID_SHORT()`）。
- **注意**：需**重启后端**（Flyway 才会执行 37 迁移、permission.json 与 i18n 才会重新加载）；若用户环境里「媒介/管理组」是自定义角色（非内置 role_id），需在角色页面手动勾选（现在树里已经有了）。
