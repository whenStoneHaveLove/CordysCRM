## 仅 admin 可见的系统设置项（模块配置/消息设置/流程设置/企业设置/系统日志）

- 需求：这 5 个「系统」二级菜单只对 admin 用户开放；「角色权限」页里对应权限项对非 admin 隐藏；要求最小改动 + 方便恢复
- **关键机制**：前端菜单/路由/按钮全部按 `permissionIds` 过滤（`frontend/.../utils/permission.ts` 的 hasPermission/hasAnyPermission；admin 由 `userStore.isAdmin`(id==='admin') 短路放行）。`permissionIds` 唯一出口是 `PermissionCache.getPermissionIds()`（登录 `UserLoginService:295` 赋值 + 接口校验 `PermissionUtils.hasPermission`）
- 实现（全在后端，3 处）：
  1. 新增 `framework/.../common/constants/AdminOnlyPermission.java`：前缀白名单 `MODULE_SETTING: / SYSTEM_NOTICE: / PROCESS_SETTING: / SYSTEM_SETTING: / OPERATION_LOG:`；**恢复 = 清空该 Set**
  2. `PermissionCache.getPermissionIds` 出口 `filter` → 非 admin 拿不到这些权限 → 前端菜单自动隐藏 + 后端 `@RequiresPermissions` 拒绝（**前端 0 改动、数据库 0 改动**）
  3. `RoleService`：`getPermissionDefinitionItems` 里非 admin 调 `removeAdminOnlyPermissions`（权限项清空后二级项/一级项一并移除）；`update` 里 `mergeAdminOnlyPermissions` 把角色原有 admin-only 权限补回请求，避免「看不见 → 保存后被真删」
- 安全性核查（防误伤业务）：`/dict/get/{module}`(MODULE_SETTING:READ) 只被 `crm-reason-drawer` 调用，而该抽屉只出现在模块配置页内 ✓；`/user/admin/option`(PROCESS_SETTING:READ) 只在 `approverSettingTab`(流程设置) ✓；`/organization/user/role/option`、`/module/form/config` 是 OR 语义 ✓
- 生效条件：非 admin 用户需重新登录或强刷（前端 permissionIds 持久化在 store）；后端无需清 `permission_cache`（过滤在缓存之外）
- `RoleControllerTests` 用的是 `SYSTEM_ROLE_*` 权限，不在白名单内，不受影响；`testGetPermissionSetting` 只断言非空 ✓

## 角色权限页：非 admin 只看「广告下单系统」（2026-09-17 追加）

- 需求升级：角色权限（`permissionTab`）的**权限清单**里，非 admin 只展示 `ADVERTISING`，其它 12 个一级组全隐藏；只有 admin 看全量
- 实现（后端 2 个文件，前端 0 改动）：
  - `AdminOnlyPermission` 新增 `NON_ADMIN_VISIBLE_MODULES = Set.of("ADVERTISING")` + `isVisibleModuleForNonAdmin(String moduleId)`（**空集合 = 不限制模块**，这是回退开关）
  - `RoleService`：**新增** `keepVisibleModulesForNonAdmin`（按一级 id 白名单过滤），**保留**第一次的 `removeAdminOnlyPermissions` 原样不动；`getPermissionDefinitionItems` / `getVisiblePermissionIds` 里按顺序各调这两个（不合并成一个方法，方便分别回退）
  - **防误删（关键）**：**新增** `mergeHiddenPermissions`（补回「角色原有、当前操作人看不见」的权限），**保留**第一次的 `mergeAdminOnlyPermissions` 原样不动，两者都调用（后者靠 submittedIds 判重不会重复添加）。因为 `updatePermissionSetting` 是整表覆盖，不补回会导致非 admin 保存后角色丢失客户/线索/商机/SYSTEM_ROLE 等权限，甚至把自己锁在角色页外
  - 初版曾把第一次的两个方法改名重写（行为是超集但丢了回退独立性），已按用户要求拆回
  - 新建角色不受补回影响（新角色无历史权限）→ 非 admin 建的角色只有广告权限
- 事实核查（勿踩坑）：
  - `PermissionDefinitionItem` / `Permission` 在 **crm 模块**（`backend/crm/.../cn/cordys/common/permission/`，包名仍是 `cn.cordys.common.permission`）→ **framework 的 `AdminOnlyPermission` 不能引用它**（编译报「程序包不存在」），过滤逻辑只能放 RoleService，常量类只留 String 判定
  - 前端 `permissionTab.vue` 的 `transferData` 只按 `licenseStore.hasLicense()` 过滤，**不按当前用户 permissionIds 过滤** → 清单完全由后端返回决定
  - `RoleLogService` 用 `getPermissionDefinitions()` 全量做日志翻译，不受过滤影响
  - `RoleControllerTests` 跑在 admin 上下文（`isCurrentAdmin()==true` 不过滤），断言不受影响

## 核实：非 admin 保存角色权限不会冲掉隐藏权限（2026-09-17 追加）

- 风险确认：`updatePermissionSetting` 是 `deletePermissionByRoleId` 全删 + 按 `enable=true` 重新插入的**整表覆盖**；前端 `permissionTab.vue` 的 `handleSave` 只遍历 `data.value`（后端返回的可见清单），隐藏项不在提交里 → 不补回必被删
- 防线：`mergeAdminOnlyPermissions` + `mergeHiddenPermissions` 在 245/247 行，**先于** 266 行 `updatePermissionSetting` 执行；两者均先判 `isCurrentAdmin()`，admin 直接 return 走原逻辑
- `updatePermissionSetting` 全仓库仅 RoleService:266 一处调用，无其它入口可绕过补回
- 已知副作用（已告知用户）：
  1. 非 admin 无法再通过页面撤销角色的隐藏权限（"看不见的不动"的必然结果），需 admin 操作
  2. 非 admin 手工构造请求提交隐藏权限 id 且 enable=true 会写库，但 `PermissionCache` 出口仍过滤，实际不生效，仅脏数据
  3. `add`(新建角色) 不补回 → 非 admin 新建的角色只有广告权限
- 自查 SQL：`SELECT permission_id FROM sys_role_permission WHERE role_id='<id>' ORDER BY permission_id;` 保存前后 diff，只应看到 `AD_*` 变化
