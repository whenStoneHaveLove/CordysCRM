## ad_order 派生金额字段 NOT NULL 修复
- 报错：`Column 'actual_media_payable_amount' cannot be null`（INSERT 时报）。
- 根因：DDL `V3.0.0_27`(actual_media_payable_amount) 与 `V3.0.0_28`(media_rebate_amount、order_income_amount) 三列均建成 `NOT NULL DEFAULT 0`。但 MyBatis insert 会显式写出实体所有字段，而 create 时这三个派生字段在 `syncOrderDownstreamMedia`（insert 之后才调用）里才被赋值 → insert 时值为 null，DEFAULT 不生效报错。
- 修复：在 `AdOrderService.create` 与 `update` 的 `adOrderMapper.insert/update` 之前，对 `actualMediaPayableAmount`/`mediaRebateAmount`/`orderIncomeAmount` 做 null → `BigDecimal.ZERO` 初始化；随后 `syncOrderDownstreamMedia` 的 update 会写回真实累加值。
- 注意：`update` 路径里 `adOrderMapper.update(order)` 在 `syncOrderDownstreamMedia` **之前**执行，故 update 主表前也需置 0。
- 编译：本地 Maven 版本过低（flatten-maven-plugin 需 3.6.3+）导致 `mvn compile` 失败，与代码无关；改动仅为 BigDecimal 置 0，类型安全。
- 提交：`2d392cfb2`（fix(ad-order): create/update 时派生金额字段置0...）

## 历史数据批量补数（派生字段为 0 的存量订单）
- 背景：V3.0.0_27/28 新增 actual_media_payable_amount/media_rebate_amount/order_income_amount 三列（NOT NULL DEFAULT 0），上线前已有订单这些字段均为 0，需补算。
- 实现：`AdOrderService` 抽取统一计算方法 `applyIncomeFromPayables(AdOrder, List<DownstreamMediaPayableDTO>)`（仅赋值不 update），把原 `syncOrderDownstreamMedia` 末尾的重算块（payableSum/actualPayableSum/mediaRebateAmount/orderIncomeAmount/paymentMethod 推导）搬入，原调用处改为调用它——逻辑唯一来源，create/update 与新补数方法共用。
- 新增 `recomputeIncomeFieldsForAll()`（`@Transactional`）：`selectList` 遍历所有订单 → 从 `ad_order_downstream_media`（`selectByOrderId`，deleted=0）读出明细映射成 DTO → `applyIncomeFromPayables` → `updateById`。幂等。
- 新增端点 `AdOrderController.POST /api/ad/order/recompute-income`（权限 `AD_ORDER_EXPORT`，@Operation 注明「数据修复」），返回重算订单数（int，由 ResultResponseBodyAdvice 包装）。本地启动后调一次即可补全部存量数据，日常不触发。
- Lints：仅既有 WARNING（重复代码段），无 ERROR。
- 提交：`2670493bc`（feat(ad-order): 新增历史数据批量补数...，抽取统一计算逻辑）
- 注意：补数端点依赖 `ad_order_downstream_media` 中已有明细数据；若某订单无下游明细，则三列会被置 0（与无明细语义一致）。
- 提交：`2670493bc`（feat(ad-order): 新增历史数据批量补数...，抽取统一计算逻辑）

## 补数 bug 修复：派生公式应"按主表金额派生"，不用明细重算主表
- 现象：用户截图中第二个订单 YYW-20260825-002 应付返点=0.00、订单收入=0.00，但实际应为 0.44（22-21.56）/ 0（21.56-21.56）。
- 根因：旧 `recomputeIncomeFieldsForAll` 走 `applyIncomeFromPayables`，用 `ad_order_downstream_media` 累加并**重写**主表 `mediaPayableAmount/actualMediaPayableAmount`。create/update 路径下这是对的（明细刚编辑，主表确实需要同步累加），但补数场景下明细与主表已不一致（旧数据）→ 把主表已正确值覆盖为错误值，并因下游明细与主表对不齐导致派生值错乱。
- 正确语义：补数只补「新加的派生列」，主表原有两个应付字段已是 source of truth，不要重算。
- 实现：
  - 新增 `applyDerivedOnlyFromOrder(AdOrder order)`：仅按主表已有金额派生 `mediaRebateAmount = mediaPayableAmount - actualMediaPayableAmount`、`orderIncomeAmount = receivableAmount - actualMediaPayableAmount`，**不动**主表金额与 paymentMethod。源字段为 null 时跳过 set（避免把已有 0 覆盖成 0 之外的值）；非 null 时用主表值计算。
  - `recomputeIncomeFieldsForAll` 改用它，**不再读取 ad_order_downstream_media**（删除 selectByOrderId + 映射循环），不再依赖明细可用性，不影响主表金额。
  - `applyIncomeFromPayables` 保留 create/update 路径继续使用（这两个场景下明细是 source of truth，需要重算主表）。
- 关键认知：**create/update 用 applyIncomeFromPayables**（明细 → 重算主表 + 派生），**补数用 applyDerivedOnlyFromOrder**（主表 → 仅派生）。两种语义不可混用。
- 提交：`2f206a70c`（fix(ad-order): 补数改为按主表金额派生应付返点/订单收入，不再重算主表金额）

## 补数口径最终版：按下游明细累加「实际应付」+ 派生「订单收入」
- 用户反馈截图：主表"实际应付"=0，但底部明细"实际应付总额（各客户累加）"=21.80，是**同一个字段 `actualMediaPayableAmount`** 不一致。
- 用户最终口径：「应该就用算两列就行，一个是订单收入，一个是实际应付」——补数**只写两列**：
  1. `actualMediaPayableAmount` = 各下游明细 `actualPayable` 之和（明细是 source of truth）
  2. `orderIncomeAmount` = `receivableAmount - actualMediaPayableAmount`
- 其他字段（mediaPayableAmount、mediaRebateAmount、paymentMethod 等）一律不动。
- 实现：
  - `applyDerivedOnlyFromOrder(AdOrder order, List<AdOrderDownstreamMedia> details)`：遍历明细累加 actualPayable → 写回主表 actualMediaPayableAmount；按 receivableAmount - 累加值算 orderIncomeAmount。
  - `recomputeIncomeFieldsForAll`：从库 `selectByOrderId(order.getId())` 读明细 → 调用 applyDerivedOnlyFromOrder → updateById。
- create/update 路径仍用 `applyIncomeFromPayables`（从 payables 重算 mediaPayableAmount/actualMediaPayableAmount/mediaRebateAmount/orderIncome/paymentMethod），不变。
- 提交：`2403b2630`（fix(ad-order): 补数改为按下游明细 actualPayable 累加写回实际应付，并算订单收入）
- 最终字段分工：
  - create/update：`applyIncomeFromPayables(order, payables)` —— 明细 → 重算主表三列 + 派生列 + paymentMethod
  - 补数：`applyDerivedOnlyFromOrder(order, details)` —— 明细 → 只补「实际应付 + 应付返点 + 订单收入」三列
- 补数三列口径（用户最终确认）：
  1. `actualMediaPayableAmount` = sum(`ad_order_downstream_media`.`actual_payable`)（明细累加）
  2. `mediaRebateAmount` = `mediaPayableAmount` - `actualMediaPayableAmount`（主表应付金额 - 实际应付）
  3. `orderIncomeAmount` = `receivableAmount` - `actualMediaPayableAmount`（实际应收 - 实际应付）
- 提交：`1a3837b76`（fix(ad-order): 补数新增应付返点列(应付金额-实际应付)，共补三列）
- 注：「应付返点」字段(media_rebate_amount)本身在 DDL V3.0.0_28 已加、实体/DTO/列表/详情均已存在，本次只是补数时把它也算出来。
