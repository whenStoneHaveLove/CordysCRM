# 2026-08-20

## 改单逻辑：保留"订单变改单审核中(60)"流程 + 记录改单前状态
- 背景：上一版重构误把"发起改单→订单变改单审核中(60)"流程整体删掉。用户确认**该流程必须保留**，只是额外要"记录改单前状态、改单后恢复"。
- 最终方案：发起改单时订单主状态切入 `CHANGE_APPROVING(60)`（停留态），同时把改单前原状态存入 `orderStatusBefore`；驳回/执行后恢复为 `orderStatusBefore`。审批通过(approve)期间订单仍停在 60，直到 execute 才恢复。

### 改动清单（在上一版基础上修正）
- `OrderStateMachine.java`：
  - **加回** 三条转换：`PENDING_EXECUTE(45)→CHANGE_APPROVING(60)`、`EXECUTING(50)→CHANGE_APPROVING(60)`、`SETTLEMENT(80)→CHANGE_APPROVING(60)`（trigger=APPLY_CHANGE）；
    以及 `CHANGE_APPROVING(60)→PENDING_EXECUTE(45)`（REJECTED）、`CHANGE_APPROVING(60)→EXECUTING(50)`（CHANGE_APPROVED）。
  - 保留 `canApplyChange`：仅 45/50/80 可发起改单（审批中10排除）。
- `AdOrderChange.java`：保留 `orderStatusBefore` 字段。
- DDL `V3.0.0_21`：保留 `order_status_before` 列（含义更新为"发起改单切60+记录前状态，驳回/执行恢复"）。
- `AdOrderChangeService`：
  - `submit`：**订单切入 60**（`order.setStatus(CHANGE_APPROVING)`），并记录 `orderStatusBefore`；日志 to=60。
  - `approve`：订单保持 60 不动（停留态）；日志 from/to 用改单前状态。
  - `reject`：订单从 60 恢复为 `orderStatusBefore`。
  - `execute`：应用快照+金额重算后，订单从 60 恢复为 `orderStatusBefore`。
- 前端 `change/create.vue`：`excluded=[0,10,60,90,100]` 不变（已发起改单的订单停在60，自然被排除，避免重复发起）。

### 关键约定（固化）
- **可改单订单状态**：待执行(45)/执行中(50)/结算中(80)；不可：草稿(0)/审批中(10)/改单审核中(60)/已归档(90)/已作废(100)。
- 发起改单→订单进 60（改单审核中）；审批通过仍停 60；驳回/执行→恢复改单前状态。
- `CHANGE_APPROVING(60)` 在 `advertisingEnum.ts` / `OrderStatus.java` 仍保留展示。

## 广告模块权限三方对齐（前端按钮 / 后端 @CsPermission / permission.json）
### 问题
- 用户"建角色分配了媒介改单提交但提交不了"；权限分配界面部分显示英文；前端按钮未按权限渲染。
### 后端现状（本就一致，未改）
- `permission.json` 16 个广告子模块权限树与 `PermissionConstants`、各 `Ad*Controller` 的 `@CsPermission` 完全一致。
- 特例（复用码）：`AD_ORDER` 无 UPDATE（编辑接口用 CREATE）；`AD_ORDER_CHANGE` 无 EXECUTE（execute 复用 SUBMIT）；`AD_CONTRACT` 归档通过/驳回都用 `ARCHIVE_APPROVE`；`AD_RECEIPT/PAYOUT` 提交用 UPDATE、通过/驳回共用 APPROVE（action 参数区分）。
- `AD_SYSTEM` 模块已废弃（仅残留翻译 `permission.ad.system.name`），permission.json 无此模块。
### 英文展示根源
- `Translator.get()` 缺 key 返回 `Not Support Key: <key>`；`permission.ad.upstreamAgent.name` / `permission.ad.downstreamMedia.name` 在 `cordys-crm_en_US.properties` **缺失**（zh_CN 齐全）。已补英文翻译。
### 前端按钮补权限（本次修改，与后端完全一致）
| 文件 | 按钮 | 权限码 |
|---|---|---|
| change/detail.vue | 提交/执行 | AD_ORDER_CHANGE:SUBMIT |
| change/detail.vue | 审批通过 | AD_ORDER_CHANGE:APPROVE |
| change/detail.vue | 驳回 | AD_ORDER_CHANGE:REJECT |
| change/create.vue | 保存 | AD_ORDER_CHANGE:CREATE |
| change/create.vue | 提交 | hasPermission(CREATE && SUBMIT)（内部先建后提） |
| order/create.vue | 保存草稿 | AD_ORDER:CREATE |
| order/create.vue | 提交 | hasPermission(CREATE && SUBMIT) |
| order/index.vue | 行内编辑 | withDirectives AD_ORDER:CREATE |
| contract/create.vue | 保存 | isEdit?AD_CONTRACT:UPDATE:AD_CONTRACT:CREATE |
| businessEntity/create.vue | 保存 | isEdit?AD_BUSINESS_ENTITY:UPDATE:AD_BUSINESS_ENTITY:CREATE |
| system/dict/index.vue | 新建/保存/行内编辑 | AD_DICT:CREATE / 动态 / AD_DICT:UPDATE |
| approval/index.vue | 通过/驳回 | 按 row.type 映射（order/change/seal/archive/receipt/payout） |
- 渲染函数按钮规范：`const permissionDirective = resolveDirective('permission');` + `withDirectives(h(NButton,...), [[permissionDirective, ['CODE']]])`；模板按钮用 `v-permission`。
- 审批中心通过/驳回权限映射函数：`approvePermissionOf(type)` / `rejectPermissionOf(type)`（archive/receipt/payout 通过与驳回共用同一码）。
### "提交不了"根因结论
1. 改单详情页提交按钮此前**无任何权限控制**（有权限无权限都显示，点后端被 @CsPermission 拦）→ 已补。
2. **会话权限不刷新**：permissionIds 是登录时一次性加载；角色改权限后目标用户必须**重新登录**。
3. 改单创建页"提交"内部先 `createAdOrderChange` 再 `submitAdOrderChange`，需 **CREATE+SUBMIT 双权限**（已做双权限按钮判断）。
- 角色分配建议：给"媒介改单"角色分配 AD_ORDER_CHANGE:READ+CREATE+SUBMIT。
