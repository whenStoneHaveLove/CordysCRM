## 巨坑：ad_order_contract 保存合同报 Duplicate entry 'uk_ad_oc'
- 报错：`AdContractService.syncOrderContract(AdContractService.java:444)` 插 `ad_order_contract` 触发 `Duplicate entry 'orderId-contractId' for key 'ad_order_contract.uk_ad_oc'`。
- 根因：`uk_ad_oc (order_id, contract_id)` **不含 deleted**（DDL 见 `V3.0.0_1__ad_system_v31.sql:322`），而合同端 `syncOrderContract` 是「先逻辑删除旧关联再 insert」。逻辑删除的行仍占用唯一键 → 第二次保存同一对关联必炸；`orderIds` 有重复项时也会炸。
- 修复（后端）：
  1. `ExtAdOrderContractMapper` 新增 `selectAllByContractId(contractId)`（`@Select ... WHERE contract_id = ?`，**不过滤 deleted**），与已有的 `selectAllByOrderId` 对称。
  2. `AdContractService.syncOrderContract` 改为「查全部（含已删）→ 不在目标集合的清 deleted=1 → 目标集合里已有的复用（deleted 复位为 0，update）→ 没有的才 insert」，`orderIds` 用 `LinkedHashSet` 去空去重。与 `AdOrderService.syncOrderContract` 的实现思路保持一致。
- **通用教训**：凡「逻辑删除 + 唯一键」的表，唯一键不含 `deleted` 时**不能先删再插**，必须复用旧行（顺带把 deleted 复位）。项目里同坑位：`ad_order_contract.uk_ad_oc`、`ad_order_downstream_media.uk_ad_odm`（订单端已处理）、`ad_payout_invoice.uk_payout_invoice_payout`（payout 端用 update 逻辑，且清除是物理删除，安全）。
- 未编译验证（Maven 离线缺 jacoco 依赖、在线编译用户不让等）；`read_lints` 无诊断。mvnw 在项目根目录，命令：`mvnw.cmd -q -pl crm -am -DskipTests -Djacoco.skip=true compile --file backend/pom.xml`。

## 巨坑：附件预览图片变下载（Content-Type 判断漏了图片）
- 现象：付款单详情/审批中心点「预览」jpg 发票，浏览器直接下载。
- 根因：`AttachmentService.resolveContentType(fileName, fallback)` **只识别 svg 和 pdf**，图片会落到 fallback `application/octet-stream` → 浏览器强制下载。
  注意 `getResource` 有两条分支：`attachment == null`（temp 临时目录）分支用 `Files.probeContentType` 能出 image/jpeg；但 **`attachment != null`（已转存的正式附件）分支只走 resolveContentType**，所以已保存的发票预览必下载。
- 修复：`resolveContentType` 增加图片分支，按扩展名返回 `image/png|gif|webp|bmp|jpeg`；同时 `isSvg` 补 null 判断（原来 `fileName.endsWith` 无 null 保护）。
- 复用：以后任何"附件预览变下载"的问题先看 `AttachmentService.resolveContentType`；预览必须 image/* 或 application/pdf 才会 inline。
- 前端预览统一写法：`/attachment/preview/{fileId}?userId=xxx`（`seal/detail.vue`、`contract/detail.vue`、`order/detail.vue`、`approval/index.vue` 一致；userId 后端未实际使用，仅保持一致）。

## 巨坑：新建 ad_* 子表 DDL 列类型必须对齐 BaseModel（String/Long）
- 报错：`Incorrect integer value: 'admin' for column 'create_user'`（INSERT ad_payout_invoice 时）。
- 根因：`cn.cordys.common.domain.BaseModel` 的字段类型是 **`String id` / `String createUser` / `String updateUser` / `Long createTime` / `Long updateTime`**（注意：**id 是 String 不是 Long，时间戳是 BIGINT 毫秒不是 DATETIME**）。我上一版 DDL 按传统习惯写成了 `id BIGINT` / `create_user BIGINT` / `create_time DATETIME` → 插入字符串 id 与 'admin' 直接报 1366。
- 模板参考：`V3.0.0_13__ad_receipt_payment.sql`（ad_receipt/ad_payment 建表），标准写法 `id VARCHAR(32) NOT NULL`、`create_time BIGINT`、`create_user VARCHAR(32)`、`organization_id VARCHAR(32)`。
- **BaseMapper.InsertSqlProvider 是非选择性 INSERT**：`INTO_COLUMNS(table.getColumns())` 会插入实体所有字段，所以表必须有实体全部字段的列（多出来的列无妨）。
- 处理方式：
  1. 改 `V3.0.0_38__ad_payout_invoice.sql` 为正确类型（新库正确）。
  2. 新增 `V3.0.0_39__fix_ad_payout_invoice_columns.sql` 做幂等 `MODIFY COLUMN` 修复已建表的库。
- **本项目的 `spring.flyway.validate-on-migrate=false`**（`backend/app/src/main/resources/commons.properties`）→ **已执行过的迁移文件可以放心改内容**，不会因 checksum 变化启动失败；但改动不会重跑，所以要另加新版本号迁移去修数据/结构。
- 迁移版本号全局唯一（ddl/dml 共用一套版本序列，Flyway location 是 `classpath:migration` 一个根）。

## 订单/合同附件 PDF 预览支持
- **合同附件**（`AdContractAttachmentService`）走 `processTemp` 转存正式目录 + 写 `sys_attachment`（`fileUrl` 即 tempFileId 也是 attachment id）→ 预览走 `getResource` 的 `attachment != null` 分支；PDF 内联预览靠上一节 `resolveContentType` 的 `isPdf` 分支，已生效。
- **订单附件**（`AdOrderAttachmentService.upload`）**只调 `uploadTemp`，从不 `processTemp`** → 文件一直躺在 `tmp/` 目录，无 `sys_attachment` 记录 → 预览走 `attachment == null` 的临时目录分支（`DefaultRepositoryDir.getTempFileDir(tempFileId)`）。
  - 临时分支的 Content-Type 也走 `resolveContentType(file.getName(), ...)`，而 temp 保存时保留了原始文件名（`file.getOriginalFilename()`），所以扩展名判断同样生效 → PDF/图片可内联预览。
  - **隐患**：`TaskCleanupJob` 每天 3 点清理临时文件，订单附件长期会 404（预览/下载失效）。若要彻底解决需让 `AdOrderAttachmentService` 也调 `processTemp`。
- 前端改动：`order/create.vue` 三个附件上传位（type 10/20/40）原本只有 n-upload 默认文件列表、**没有预览入口**；现改为 `:show-file-list="false"` + 自渲染列表（`.attach-file-list`），每项带「预览/下载/删除」。
  1. 预览：新选文件（还在 `pendingFiles` 里的 `File`）用 `URL.createObjectURL` 本地 blob 打开；已保存附件走 `/attachment/preview/{fileUrl}`；非 PDF/图片（doc/xls 等）自动降级为下载。
  2. 删除：自定义按钮调 `handleAttachRemove(type, file)` → 内部先 `handleFileRemove`（返回 false 则不删）再按 `id` 从 `fileListTypeX` 过滤，并按原始 `File` 对象兜底清 `pendingFiles`。
  3. `handleFileSelect` 里原来的 `opts.file.id = _key` **改不到列表对象**（naive-ui `createSettledFileInfo` 会对 custom-request 收到的 file 做浅拷贝），所以补了一句按 `f.file === rawFile` 定位 `fileListTypeX` 里的真实项并回写 `id = _key`，否则暂存文件删不掉、仍会被上传。
  4. 查 naive-ui 内建 `file` 插槽不可靠（`es/upload` 里查不到 `slots.file`），改用项目已有的「自渲染列表」方案更稳。
- 其余页面（`order/detail.vue`、`contract/detail.vue`、`contract/create.vue`、`seal/detail.vue`）本来就有预览按钮，走 `/attachment/preview/{id}`，后端 Content-Type 修好后 PDF 已可直接内联预览，无需改动。
