## 巨坑：ad_order_contract 保存合同报 Duplicate entry 'uk_ad_oc'
- 报错：`AdContractService.syncOrderContract(AdContractService.java:444)` 插 `ad_order_contract` 触发 `Duplicate entry 'orderId-contractId' for key 'ad_order_contract.uk_ad_oc'`。

## 巨坑：附件预览图片变下载（Content-Type 判断漏了图片）
- 现象：付款单详情/审批中心点「预览」jpg 发票，浏览器直接下载。
- 根因：`AttachmentService.resolveContentType(fileName, fallback)` **只识别 svg 和 pdf**，图片会落到 fallback `application/octet-stream` → 浏览器强制下载。
  注意 `getResource` 有两条分支：`attachment == null`（temp 临时目录）分支用 `Files.probeContentType` 能出 image/jpeg；但 **`attachment != null`（已转存的正式附件）分支只走 resolveContentType**，所以已保存的发票预览必下载。
- 修复：`resolveContentType` 增加图片分支，按扩展名返回 `image/png|gif|webp|bmp|jpeg`；同时 `isSvg` 补 null 判断（原来 `fileName.endsWith` 无 null 保护）。
- 复用：以后任何"附件预览变下载"的问题先看 `AttachmentService.resolveContentType`；预览必须 image/* 或 application/pdf 才会 inline。
- 前端预览统一写法：`/attachment/preview/{fileId}?userId=xxx`（`seal/detail.vue`、`contract/detail.vue`、`order/detail.vue`、`approval/index.vue` 一致；userId 后端未实际使用，仅保持一致）。

## 附件预览 401 排查（用户报 `/attachment/preview/{id}?userId=admin` 打开 401）
- 结论：**与本轮 eml 改动无关**（只动了 ad 订单附件相关 4 个 Java + 2 个 vue，未碰 security）。
- 链路：`ShiroFilter.addFileAccessFilters` 把 `/attachment/preview/**`、`/attachment/download/**`、`/pic/**` 挂 `authf` → `FileAccessAuthFilter` 只认 **Cookie `F_A_TOKEN`** → `FileAccessTokenUtils.getSessionId` 用 `cordys.secret.key`(注入到 `SessionUser.secret`) AES 解密 → `SessionUtils.sessionExists(sessionId)` 查 **Redis**（`RedisIndexedSessionRepository.findById`）。
- 401 三种根因：①没重新登录 / 无痕窗口直接粘 URL（无 cookie）；②Redis 重启或清库，session 不存在；③`cordys.secret.key` 变了，旧 cookie 解不开。
- 快速判断：F12 → Application → Cookies 里有没有 `F_A_TOKEN`；有的话基本就是 Redis session 没了或 secret 变了 → 重新登录即可。
- 注意：`13ac16a7c refactor: remove unused public path filters from ShiroFilter`（2026-07 上游提交）已把这些路径从 anon 移除，所以老版本能匿名预览、现在不行。
- 补充机制差异（解释"接口正常、只有预览 401"）：普通 `/api/**` 走 `apikey, csrf, authc`，`ApiKeyFilter` 支持 header token（`CommonBeanFactory.getUser`）自动 `subject.login`；而 `window.open` 打开预览**带不上自定义 header**，只能靠 cookie → 所以页面一切正常时预览照样可能 401。
- 过滤器链顺序：`ShiroFilterFactoryBean` 的 `filterChainDefinitionMap` 是 LinkedHashMap，`/attachment/preview/**`(authf) 在 `/**`(apikey,csrf,authc) 之前 → 预览确实走 authf，不走 authc。
- 其他确认点：vite dev proxy 有 `/attachment` 规则（rewrite 仅处理 `/front/attachment` 前缀，对预览路径不改写，原样转发）；`cordys.secret.key` 为固定值 `9a9rdqPlTqhpZzkq`；`spring.session.timeout=43200s`（12h，存 Redis）。

## ★ 预览 401 根因已定位（2026-09-16，实测验证）
- **实测**：Node 脚本模拟登录（RSA 公钥来自 `GET /get-key`，返回体是 `{code,data}` 包一层，`data` 才是 Base64 SPKI；`LoginRequest.getUsername/getPassword` 用私钥解密，JSEncrypt 是 PKCS#1 v1.5）→ 拿到 `Set-Cookie: F_A_TOKEN=...` → 带该 cookie 请求 `/attachment/preview/...` → **200 + application/pdf**。证明后端预览链路、`FileAccessAuthFilter`、我的改动**全部正常**。
- **根因**：`backend/crm/.../config/SessionConfig.java` 用的是 `HeaderHttpSessionIdResolver(SessionConstants.HEADER_TOKEN)` —— **会话只认 header `X-AUTH-TOKEN`（值=sessionId，前端存 localStorage，登录态 30 天），根本不靠 cookie**。而 `window.open` 打开的预览新窗口**带不上自定义 header**，只能靠 `F_A_TOKEN` cookie；该 cookie 是 `HttpOnly + MaxAge=-1`（会话级），且**只在 `/login` 成功那一刻写入**（`LoginController` 第 102 行）。
- 所以：只要 `F_A_TOKEN` 丢失（关浏览器、清缓存、换浏览器/换 host、无痕），而 localStorage 里登录态还在 → 页面一切正常（header 鉴权），但**所有模块预览一律 401**（订单/合同/用印/付款单全覆盖）。
- 注意：`F_A_TOKEN` 是 HttpOnly，`document.cookie` **看不到**（用户截图里那条命令看不到它是正常的），必须看 DevTools → Application → Cookies。
- **推荐修复（最小改动）**：在 `LoginController.isLogin()` 里补写 cookie（该方法每次进系统/刷新都会调用，且此时 `SessionUtils.getSessionId()` 一定是当前有效 sessionId）：
  `FileAccessTokenUtils.setAccessCookie(httpServletResponse, SessionUtils.getSessionId(), httpServletRequest.isSecure());`
  需要给 `isLogin()` 加 `HttpServletRequest/HttpServletResponse` 参数。这样刷新页面即自动补 cookie，永不复发。
- 备选修复：前端预览改 `CDR.get(..., responseType:'blob')` → `URL.createObjectURL`，彻底不依赖 cookie。
- 临时恢复手段（给用户）：**退出登录 → 重新登录**（仅刷新页面不会写 cookie）。
