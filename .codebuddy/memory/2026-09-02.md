## 付款单新增「付款单类型」（订单类型 / 非订单类型）

### 需求
- 付款单加「付款单类型」：`10` 订单类型（默认）/ `20` 非订单类型
- **订单类型**：必须选关联订单，客户明细由订单带出（可多客户），保持原样
- **非订单类型**：
  - 隐藏「关联订单」和订单带出的客户明细卡片
  - 显示「下游客户」下拉手动选择，选完 →「账户信息」二级联动（锁定该客户账户）
  - 仅支持一条明细
  - 「本次付款」字段隐藏，值 = 付款金额
- 审核中心付款单也要显示付款单类型；非订单类型不展示订单信息

### 关键设计决策
- 字段命名用 **`bill_type`**，**不要**叫 `type`。已有的 `type` 是「10普通付款/20坏账」，两者含义不同，混用会出大问题。
- **`ad_payment.order_id` 原本是 `NOT NULL`**，非订单类型没有订单 → 迁移里必须先 `MODIFY` 成 NULL，否则插入必失败。

### 改动清单

**数据库** `V3.0.0_29__ad_payment_bill_type.sql`（当时 ddl 最大版本号 28）
```sql
ALTER TABLE ad_payment MODIFY COLUMN `order_id` VARCHAR(32) NULL COMMENT '关联订单(非订单类型时为空)';
ALTER TABLE ad_payment ADD COLUMN `bill_type` TINYINT NOT NULL DEFAULT 10 COMMENT '付款单类型:10订单类型/20非订单类型' AFTER `payment_no`;
```

**后端**
- 新常量 `cn.cordys.crm.ad.payout.constants.PayoutBillType`（ORDER=10/NON_ORDER=20，含 `ofOrDefault()` 与 `isOrder()`）
- `AdPayout` / `AdPayoutSaveRequest` / `AdPayoutDetailResponse` / `AdPayoutListResponse` 加 `billType`（+响应加 `billTypeLabel`）

  - `detail()` 非订单类型跳过订单/合同加载
  - `page()` 补 billType/billTypeLabel

**前端**

### 详情弹窗非订单类型隐藏返点列
- 付款单详情（`payout/index.vue`）和审批中心付款单详情（`approval/index.vue`）的明细表，原本不管类型都展示「应付/不记返/返点方式/返点值/返点金额/实际应付」六列。非订单类型时这六列全 0，没意义。
- 改动：两处模板都加 `v-if="!isNonOrderBill"` / `v-if="!isDetailPayoutNonOrder"`，保留「序号/下游客户/本次付款/收款账户」四列。
- 状态/计算属性：
  - `payout/index.vue`：新增 `isNonOrderBill = computed(() => detail.billType === NON_ORDER)`，**必须定义在 `detail = reactive(...)` 之后**，否则触发 `no-use-before-define` lint。
  - `approval/index.vue`：新增 `detailPayoutBillType = ref(ORDER)` 与 `isDetailPayoutNonOrder = computed(...)`，在 `openDetail` 重置为默认 ORDER、在 payout 分支的 `loadDetail` 里回填 billType。
- 教训：详情弹窗的状态不要复用 form 的 `isOrderBill`——`form` 可能被 `resetForm`/`openEdit` 等操作清空，导致表格列错乱。要为详情另起一个独立的 computed。
- 验证：`vue-tsc --noEmit`、`eslint --fix` 均通过。

### 补充迁移：`V3.0.0_30__ad_payment_media_order_id_nullable.sql`
- 运行时报错 `Column 'order_id' cannot be null`（INSERT ad_payment_media 时）。
- 原因：非订单类型时 `ad_payment_media.order_id`（冗余列）为 null，而该列 NOT NULL。
- **教训：`V3.0.0_29` 只放宽了 `ad_payment.order_id`，遗漏了 `ad_payment_media.order_id`。改表约束时要顺着 INSERT 链路把所有冗余列一起查。**

### `AdPayoutService.saveMediaDetails` 空值兜底
- 非订单类型明细只填 mediaId/mediaName/paidAmount/accountId，其余全 null，而这些列也 NOT NULL：
  - `order_downstream_media_id` NOT NULL → 兜底 `""`
  - `payable_amount` / `no_rebate_amount` / `rebate_value` / `rebate_amount` / `actual_payable` NOT NULL DEFAULT 0 → **显式 INSERT NULL 仍会失败**（DEFAULT 只在省略列时生效），统一兜底 `BigDecimal.ZERO`
- 加了两个重载辅助：`nvl(String)` → `""`，`nvl(BigDecimal)` → `ZERO`。
- **教训（重要）：MySQL 的 `NOT NULL DEFAULT 0` 不等于"传 null 也能过"。MyBatis 全列 INSERT 会显式写 NULL，必须代码兜底。**

### 踩坑
1. `ad_payment.order_id` 是 NOT NULL → 必须 MODIFY 成 NULL，非订单类型才能保存。
2. `ad_payment_media.order_id` 同样是 NOT NULL → 需 `V3.0.0_30` 一并放宽。
2. `no-use-before-define`：新加的 `onBillTypeChange` 用到了 `mediaOptions`/`resetMediaDraft`，必须定义在它们**之后**（放在 `resetMediaDraft` 下面）。
3. `getAdDownstreamMediaAccounts` 没在 `@/api/modules` 导出，只在 lib-shared 的 api 里 → vue-tsc TS2724，需在 `api/modules/index.ts` 的 adDownstreamMediaApi 解构里补上。
4. 避免把 `bill_type` 与已有 `type`（普通付款/坏账）混淆，命名与注释都要区分清楚。

### 验证
- `vue-tsc --noEmit` 通过
- `eslint --fix` 0 error（payout/approval/advertisingEnum/api modules）
- `mvn -pl crm -am compile` 通过

## Flyway 版本冲突修复：付款单付款权限迁移 3.0.0.16 → 3.0.0.21

### 问题
后端启动报错：`FlywayException: Found more than one migration with version 3.0.0.16`
冲突双方：
- `backend/crm/src/main/resources/migration/3.0.0/ddl/V3.0.0_16__drop_contract_order_id.sql`（已存在）
- `backend/crm/src/main/resources/migration/3.0.0/dml/V3.0.0_16__ad_payout_pay_permission.sql`（本次新增）
Flyway 版本号跨 `ddl`/`dml` 目录全局唯一。

### 修复
- `git mv` 将 DML 文件重命名为 `V3.0.0_21__ad_payout_pay_permission.sql`
- 修正脚本内容：仅授予 `org_admin` 默认 `AD_PAYOUT:PAY` 权限，不再写死给 `ROLE_BOSS` / `ROLE_FINANCE`
- 删除 `backend/crm/target/classes/migration/3.0.0/dml/` 下旧的编译副本
- 提交：`fix(ad): 修复 Flyway 版本 3.0.0.16 冲突，付款单付款权限迁移改为 3.0.0.21 并仅授予 org_admin`
- 后又发现 `V3.0.0_21` 在 ddl 目录也被占用（`V3.0.0_21__ad_order_change_add_order_status_before.sql`），再次改为 `V3.0.0_32`。
- 提交：`fix(ad): 付款单付款权限迁移改用未占用版本 3.0.0.32 避免与 ddl 冲突`

### 教训
- **新增 Flyway 迁移前必须同时检查 `ddl` 和 `dml` 目录**，版本号全局唯一，不是按目录独立。
- 权限分配脚本只应保证内置管理员（`org_admin`）拥有新权限，业务角色（财务/老板等）由用户在「系统-角色权限」界面自行分配，避免写死。
- 提交前用 `git status --short` 复核，避免把无关文件或旧编译产物带入提交。

## 权限点"付款"显示为 `Not Support Key: permission_pay`

### 问题
角色权限配置页中，`AD_PAYOUT:PAY` 显示成 `Not Support Key: permission_pay`（后端 `Translator.get` 未找到 i18n key 的 fallback）。

### 修复
在 `backend/crm/src/main/resources/i18n/cordys-crm_zh_CN.properties` 和 `cordys-crm_en_US.properties` 中分别添加：
```properties
permission.pay=付款
permission.pay=Pay
```
提交：`fix(i18n): 添加权限点 permission.pay 中英文翻译`

### 教训
- 后端 `permission.json` 只定义权限 ID，权限操作名称走后端 i18n properties，key 规则为 `permission.<action>`。
- 新增自定义 action（如 PAY）时，必须同步在 `cordys-crm_zh_CN.properties` / `cordys-crm_en_US.properties` 加翻译，否则角色权限页面会显示 `Not Support Key`。
- 常见 action 已有翻译：`permission.read/view/add/create/update/edit/delete/import/export/download/recover/pick/assign/merge/archive/voided/review/media/boss/finance/approve/stage/payment/pay_media_prepay/pay_media_postpay`。
